### Plan-vs-code conflicts and decisions
- C-1 Stage labels. T0 accepted proposal: add the three keys to `notices.STAGE_TITLES`. Existing pinned test `tests/test_notices.py:126` (`test_the_stage_titles_are_the_specified_ones`) asserts `STAGE_TITLES` equals exactly the four M1/M2 titles. Resolved without editing that test: the labels live on the stage objects (`StrategyStage.label`, read by `_stage_label`) and in a new add-only `notices.STRATEGY_TITLES`; the run manager uses `TITLES = {**STAGE_TITLES, **STRATEGY_TITLES}` for stage entries. `orchestrator.STAGE_LABELS` not extended; `/api/meta` still publishes FULL_STAGES (four).
- C-2 `WARNING_LABELS` entries added in notices.py (add-only, beyond the brief's "STAGE_TITLES" wording) so a strategy warning such as "Assessing strengths and risks: skipped because the request reached its time limit." maps to the stage and the existing time-limit/cancel rules. No existing warning starts with these labels, so existing notices are unchanged (full suite green).
- C-3 Skip wording. 5.2 says reason "Needs at least one finished analysis."; 11.2 says "Time limit reached.". Code convention is "{label}: skipped because ...", so `SKIP_NO_ANALYSIS = "{label}: skipped because it needs at least one finished analysis."` and the existing `SKIP_NO_TIME` / `SKIP_CANCELLED` are reused.
- C-4 Notice text for strategy stages is T9. Until T9 adds `strategy_stage_skipped` and strategy titles to the notice templates, the stage-tracker message of a no-analysis skip is the notices fallback ("A quality check adjusted part of the results. Open the details to see what changed."), and template `{stage}` names render "This step" / "One step" because `STAGE_TITLES` has no strategy keys. No field path leaks. Recorded for T9.
- C-5 Output tokens (11.1.3, I-06). Gemini: `generate_json` sets no `max_output_tokens`, so the model default applies, which is above the 2,000-3,500 tokens a stage needs; adding a value would introduce a cap (and Gemini thinking tokens count against it), so the Gemini request is left byte-identical. Groq: `MAX_COMPLETION_TOKENS = 4096` covers reasoning plus reply; for strategy stages only it is raised to `STRATEGY_MAX_OUTPUT_TOKENS = 6144` through a ContextVar scope opened by `StrategyStage.run`. Every other call sends 4096 as before. 12.6 has no setting for this, so it is a code constant and config.py/.env.example are not touched. Open risk for T20: Groq rejects requests whose prompt plus requested completion tokens exceed the plan's TPM (the existing tests already model a 413 "Request too large"); a large digest plus 6144 may hit this on the base plan. Measure in T20 and tune the constant.
- C-6 Strategy-only job budget. D-11 defines the deadline only for `include_strategy` runs. The strategy job on a saved run uses `STRATEGY_TIME_LIMIT_S` alone (no stages 1-4 run).
- C-7 Strategy-only job and cancel. 5.5 shows only running -> done for the job. A cancel during a strategy job therefore ends the run `done` with `result_status` `partial` and the remaining strategy stages `cancelled`; an `include_strategy` run cancelled between strategy stages ends `cancelled` like any other run.
- C-8 Strategy-only job bookkeeping: `started_at` and `created_at` keep the original values; `finished_at` becomes the job's end; `duration_s` and `timings.total` are the saved total plus the job's time; warnings of the saved result are kept; errors and timings of the re-run stages are replaced.
- C-9 Scope left to T8: `start_strategy` has no `mode` and never raises `StrategyAlreadyCompleteError`; it runs all three stages (the `all` behaviour), resetting existing strategy entries in place. Constraints: given -> stored `constraints_json` -> the saved result's constraints. No route, response model, `has_strategy` or meta change.
- C-10 Production stage lists hold `PendingStrategyAgent` placeholders until T5-T7 register the real agents; a seven-stage run with them ends `partial` with three plain stage errors. Not reachable through the API in T4.
- C-11 Known edge: if the server stops during a strategy job, the T2 store marks the row `failed` (MSG_INTERRUPTED) on the next start; `result_json` (the earlier result) is kept, `result_status` is NULL while the job runs. Store behaviour is T2's and was not changed.
